## 项目概述

**Insurance Skills** 是一个面向保险领域的开源 Skill 基础设施平台，旨在围绕保险业务中的典型场景，推动 Skill 的**结构化沉淀、标准化描述、可比性评价与工程化复用**。项目服务于保险 Agent、Copilot、流程自动化、知识服务与业务智能化等多类应用方向，强调在保险这一强规则、强流程、强约束领域中，构建具有领域适配性、方法一致性与长期演进能力的 Skill 体系。

### 项目属性

| 属性 | 内容 |
| --- | --- |
| 项目名称 | Insurance Skills |
| 项目类型 | 开源 Skill 基础设施平台 |
| 领域定位 | 保险场景 |
| 发起团队 | 复旦大学许闲教授团队 |
| 核心目标 | 汇聚、组织、评估与复用保险领域 Skill |
| 面向对象 | 保险公司、保险科技团队、Agent 产品团队、研究者与开发者 |

### 项目关注的核心问题

| 核心问题 | 说明 |
| --- | --- |
| 如何组织保险领域 Skill | 使 Skill 能够被系统化收集、识别、分类与检索 |
| 如何评价保险领域 Skill | 使 Skill 具备可比较、可复核、可解释的质量判断基础 |
| 如何沉淀保险领域 Skill | 使 Skill 能够服务于后续 Agent 构建、流程编排与平台接入 |

因此，Insurance Skills 并不只是一个 Skill 列表，而是一个面向保险场景的 **开放能力基础设施项目**。

## 研究背景与问题提出

保险业务具有鲜明的领域属性。与一般性的数字化服务场景相比，保险场景通常表现出更强的规则约束、更复杂的业务链条以及更高的风险控制要求。

### 保险场景的领域特征

| 领域特征 | 说明 |
| --- | --- |
| 业务链条长 | 覆盖咨询、投保、核保、保单服务、理赔、续保、客服、风控等多个环节 |
| 规则约束强 | 条款、制度、权限、监管要求与合规边界复杂 |
| 场景差异深 | 不同险种、渠道、组织角色与流程节点的能力需求显著不同 |
| 风险容忍度低 | 对准确性、可追溯性、稳定性、安全性与可解释性要求更高 |

### 当前面临的主要问题

| 问题 | 具体表现 |
| --- | --- |
| 领域 Skill 缺少统一组织框架 | Skill 分散在不同项目、文档与实现中，缺乏统一入口 |
| Skill 描述方式缺乏一致性 | 命名、边界、输入输出与依赖关系差异较大 |
| Skill 质量缺少透明评价机制 | 难以形成统一、可复核的质量判断基础 |
| Skill 与实际落地之间存在断层 | 适用场景、维护成本、安全边界与接入条件不够明确 |

Insurance Skills 正是在这一背景下提出，试图以更规范的结构、更清晰的方法与更开放的协作方式，推动保险领域 Skill 由“碎片化存在”走向“平台化沉淀”。

## 项目愿景

Insurance Skills 希望面向保险行业构建一个开放、可持续演进的 Skill 生态基础设施，使保险领域 Skill 能够在统一框架下被发现、理解、评价、复用与集成。

### 愿景框架

| 维度 | 目标 |
| --- | --- |
| 发现 | 通过结构化方式实现 Skill 的检索、识别与定位 |
| 理解 | 通过标准化描述明确 Skill 的边界、用途与依赖 |
| 评价 | 通过统一维度比较 Skill 的质量与成熟度 |
| 复用 | 使 Skill 成为可迁移、可沉淀的长期能力资产 |
| 集成 | 为 Agent、Copilot 与业务流程系统提供接入基础 |

### 长期目标

| 方向 | 说明 |
| --- | --- |
| 结构化 | 推动 Skill 从零散描述走向统一建模 |
| 标准化 | 建立一致的描述与评价框架 |
| 平台化 | 支持 Skill 的检索、比较与持续扩展 |
| 生态化 | 形成高校、产业与开发者协作共建机制 |

## Skill 评测框架

Insurance Skills 采用结构化质量评估框架，对 Skill 的文档表达、信息覆盖、执行可行性、长期维护性与风险控制能力进行综合分析。当前评分体系由**评分准则总览、分值区间解释与规则来源**三部分共同构成，并已纳入项目配置与处理流程。

### 一级评价维度

| 维度 | 含义 |
| --- | --- |
| 清晰度（clarity） | 衡量 Skill 文档是否表达清楚、结构是否容易理解 |
| 完整度（completeness） | 衡量 Skill 是否覆盖关键字段、章节与依赖信息 |
| 可操作性（operability） | 衡量用户是否能够依据文档直接执行并复现结果 |
| 可维护性（maintainability） | 衡量 Skill 是否便于版本跟踪、持续更新与长期维护 |
| 安全性（security） | 衡量凭证、数据传输、影响范围与破坏性操作的风险控制能力 |

### 评分依据

| 评分依据 | 说明 |
| --- | --- |
| 摘要与命名 | 是否能够准确、清晰地表达 Skill 的用途 |
| 安装与使用说明 | 是否提供足够的搭建、运行与使用说明 |
| 示例质量 | 是否存在完整示例，且便于理解与复现 |
| 依赖与限制 | 是否明确说明依赖条件、边界与使用限制 |
| 异常处理 | 是否提供异常情况说明与处理建议 |
| 版本与更新信息 | 是否具备版本信息、变更记录与维护痕迹 |
| 风险相关信息 | 是否涉及凭证、数据暴露、破坏性操作等安全因素 |

这些信号共同构成 Skill 质量评估的结构化依据。

### 二级评价准则

| 一级维度 | 二级准则 |
| --- | --- |
| 清晰度（clarity） | 命名质量、结构质量、描述质量、示例清晰度 |
| 完整度（completeness） | 字段覆盖、证据覆盖、章节覆盖、依赖完整性 |
| 可操作性（operability） | 搭建难易、执行清晰、异常指引、可复现性 |
| 可维护性（maintainability） | 版本跟踪、模块化程度、抗过时能力、文档健康度 |
| 安全性（security） | 凭证安全、数据暴露风险、影响范围控制、破坏性控制 |

### 分值区间解释

| 分数区间 | 中文解释 | 使用建议 | 常见状态 |
| --- | --- | --- | --- |
| 0–3 | 基础薄弱 | 不建议直接用于生产场景，应优先补充文档、边界与说明 | 信息缺失较多，步骤不可执行 |
| 4–6 | 可用但存在明显缺口 | 可在受控范围内试用，建议补充示例与异常处理 | 能理解部分流程，但复现稳定性不足 |
| 7–8 | 质量较好 | 可用于常规场景，建议持续补充维护信息 | 结构较清晰，执行路径较明确 |
| 9–10 | 高质量 | 可作为模板、基线 Skill 或复用对象 | 文档完善，风险控制较好，可审计性较强 |

### 方法论意义

| 方法论问题 | Insurance Skills 的回答 |
| --- | --- |
| Skill 是否被清楚定义 | 通过清晰度与完整度维度进行描述质量判断 |
| Skill 是否具备足够执行依据 | 通过可操作性维度衡量执行路径与复现能力 |
| Skill 是否适合长期使用 | 通过可维护性与安全性维度评估长期稳定性与风险边界 |

因此，该框架不仅用于描述 Skill 的“质量水平”，更用于提升 Skill 的**可比较性、可审计性与可集成性**。

## 评分规则来源

Insurance Skills 的质量评分并非仅停留在文档层面，而是已在项目配置与处理流程中落地生效。LLM 主要用于补充部分维度的证据抽取，但并非唯一评分来源。平台最终强调的是结构化信号、规则映射与流程校验共同作用下的质量评估结果。

| 主题 | 结论 |
| --- | --- |
| 质量分范围 | 每个质量维度得分均为 0–10 |
| 质量维度 | clarity / completeness / operability / maintainability / security |
| 主流程生效规则 | 当前由 merge 阶段计算并写入质量字段 |
| LLM 补充 | LLM 用于补充 clarity / completeness / operability 的部分证据，但非唯一来源 |
| 边界校验 | 主分与子分均需满足 0–10 的范围约束 |

> 更完整的实现细节、映射逻辑与方法说明，建议单独放入 `docs/evaluation-framework.md` 或 `docs/methodology.md` 中，而不在 README 首页展开。
