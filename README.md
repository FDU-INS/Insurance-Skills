## 项目概述

**Insurance Skills** 是一个面向保险领域的开源 Skill 基础设施平台，旨在围绕保险业务中的典型场景，推动 Skill 的**结构化沉淀、标准化描述、可比性评价与工程化复用**。项目服务于保险 Agent、Copilot、流程自动化、知识服务与业务智能化等多类应用方向，强调在保险这一强规则、强流程、强约束领域中，构建具有领域适配性、方法一致性与长期演进能力的 Skill 体系。

与一般性的工具集合或案例仓库不同，Insurance Skills 更关注三个层面的核心问题：  
一是如何围绕保险场景对 Skill 进行系统化组织，使其能够被持续收集、识别、分类与检索；二是如何建立面向保险领域的评价框架，使 Skill 具备可比较、可复核、可解释的质量判断基础；三是如何推动 Skill 的长期沉淀与复用，使其真正服务于后续 Agent 构建、流程编排与平台接入。

从这个意义上看，Insurance Skills 并不只是一个 Skill 列表，而是一个面向保险场景的 **开放能力基础设施项目**。

## 研究背景与问题提出

保险业务天然具有较强的领域复杂性。相较于一般性的数字化服务场景，保险业务往往涉及更长的流程链条、更复杂的规则约束以及更高的风险控制要求。尤其是在 Agent、Copilot 和流程自动化等应用加速落地的背景下，Skill 已逐步成为连接模型能力、业务知识与流程执行的重要中介层。

然而，当前保险场景下的 Skill 建设仍然存在明显的结构性问题。大量能力分散在不同项目、文档、方案和工具中，缺乏统一的组织与沉淀方式；同类 Skill 在命名、边界、输入输出与依赖条件上的描述方式不一致，导致复用成本较高；与此同时，针对 Skill 的质量判断也常常缺乏透明、可复核的标准，影响选型与比较效率。即便识别出潜在可用的 Skill，其适用边界、接入条件、维护成本与安全约束往往也不够清晰，进而制约了实际落地。

Insurance Skills 正是在这一背景下提出。项目试图以更规范的结构、更清晰的方法与更开放的协作方式，推动保险领域 Skill 由“碎片化存在”走向“平台化沉淀”。

### 保险场景的领域特征

| 领域特征 | 说明 |
| --- | --- |
| 业务链条长 | 覆盖咨询、投保、核保、保单服务、理赔、续保、客服、风控等多个环节 |
| 规则约束强 | 条款、制度、权限、监管要求与合规边界复杂 |
| 场景差异深 | 不同险种、渠道、组织角色与流程节点的能力需求显著不同 |
| 风险容忍度低 | 对准确性、可追溯性、稳定性、安全性与可解释性要求更高 |

### 当前面临的主要问题

| 问题 | 具体表现 |
| --- | --- |
| 领域 Skill 缺少统一组织框架 | Skill 分散在不同项目、文档与实现中，缺乏统一入口 |
| Skill 描述方式缺乏一致性 | 命名、边界、输入输出与依赖关系差异较大 |
| Skill 质量缺少透明评价机制 | 难以形成统一、可复核的质量判断基础 |
| Skill 与实际落地之间存在断层 | 适用场景、维护成本、安全边界与接入条件不够明确 |

## 项目愿景

Insurance Skills 希望面向保险行业构建一个开放、可持续演进的 Skill 生态基础设施，使保险领域 Skill 能够在统一框架下被发现、理解、评价、复用与集成。

这意味着，Skill 不再只是零散的功能描述或局部实现，而应当逐步成为能够被组织、被分析、被比较、被迁移的长期能力资产。项目更关注的是：如何让 Insurance Skills 成为保险领域智能化建设中的能力底座，而不仅是某一阶段的项目集合。

### 愿景框架

| 维度 | 目标 |
| --- | --- |
| 发现 | 通过结构化方式实现 Skill 的检索、识别与定位 |
| 理解 | 通过标准化描述明确 Skill 的边界、用途与依赖 |
| 评价 | 通过统一维度比较 Skill 的质量与成熟度 |
| 复用 | 使 Skill 成为可迁移、可沉淀的长期能力资产 |
| 集成 | 为 Agent、Copilot 与业务流程系统提供接入基础 |

## 平台定位

Insurance Skills 的平台定位不是单点产品展示，也不是单纯的 Skill 清单维护，而是围绕保险智能化应用构建领域能力的组织与评价基础设施。

从功能层面看，它承担保险领域 Skill 的持续汇聚与归档；从方法层面看，它提供面向保险场景的结构化描述范式与质量评价框架；从工程层面看，它为后续的 Agent 构建、流程编排与系统接入提供基础参考。

| 定位层次 | 说明 |
| --- | --- |
| 领域能力汇聚平台 | 围绕保险业务场景持续收集和沉淀相关 Skill |
| 领域能力评价平台 | 围绕表达质量、覆盖程度、执行可行性、维护能力与风险控制能力建立统一评价机制 |
| 领域能力基础设施平台 | 为保险 Agent、Copilot、流程自动化与业务智能化建设提供底层能力组织方式、评价依据与集成参考 |

## 核心能力体系

Insurance Skills 当前围绕以下能力展开建设。它既关注 Skill 的“有没有”，也关注 Skill 的“怎么描述”“如何评价”以及“能否复用”。

| 能力模块 | 说明 |
| --- | --- |
| Skill 汇聚 | 面向保险领域多渠道汇聚 Skill 样本，形成开放能力资源池 |
| Skill 组织 | 基于业务环节、场景类型、能力标签、适用对象等维度进行结构化分类 |
| Skill 描述 | 建立统一描述范式，明确名称、功能、场景、输入输出、边界、依赖与约束 |
| Skill 评价 | 通过结构化评估框架，对 Skill 的质量、成熟度与风险控制能力进行多维分析 |
| Skill 对比 | 支持同类 Skill 的横向比较，为选型与优先级排序提供依据 |
| Skill 复用与集成参考 | 为 Agent 构建、流程编排、系统接入与能力迁移提供方法支撑 |

## Skill 评测框架

Insurance Skills 采用结构化质量评估框架，对 Skill 的文档表达、信息覆盖、执行可行性、长期维护性与风险控制能力进行综合分析。当前评分体系由**评分准则总览、分值区间解释与规则来源**三部分共同构成，并已纳入项目配置与处理流程。

这一框架的核心目的，不是简单给出一个分数，而是为 Skill 提供一套更可复核、可解释、可比较的评价依据，从而支持后续的筛选、比较与复用。

### 一级评价维度

| 维度 | 含义 |
| --- | --- |
| 清晰度（clarity） | 衡量 Skill 文档是否表达清楚、结构是否容易理解 |
| 完整度（completeness） | 衡量 Skill 是否覆盖关键字段、章节与依赖信息 |
| 可操作性（operability） | 衡量用户是否能够依据文档直接执行并复现结果 |
| 可维护性（maintainability） | 衡量 Skill 是否便于版本跟踪、持续更新与长期维护 |
| 安全性（security） | 衡量凭证、数据传输、影响范围与破坏性操作的风险控制能力 |

### 评分依据

Insurance Skills 的评分不依赖单一主观判断，而是综合考察 Skill 在多个方面的表现，包括但不限于：

- 摘要与命名是否清晰
- 安装与使用说明是否充分
- 示例是否完整且便于复现
- 依赖、限制与异常处理是否明确
- 是否具有版本信息与更新记录
- 是否涉及凭证、数据暴露、破坏性操作等风险因素

这些信号共同构成 Skill 质量评估的结构化依据。

### 二级评价准则

| 一级维度 | 二级准则 |
| --- | --- |
| 清晰度（clarity） | 命名质量、结构质量、描述质量、示例清晰度 |
| 完整度（completeness） | 字段覆盖、证据覆盖、章节覆盖、依赖完整性 |
| 可操作性（operability） | 搭建难易、执行清晰、异常指引、可复现性 |
| 可维护性（maintainability） | 版本跟踪、模块化程度、抗过时能力、文档健康度 |
| 安全性（security） | 凭证安全、数据暴露风险、影响范围控制、破坏性控制 |

### 分值区间解释

| 分数区间 | 中文解释 | 使用建议 | 常见状态 |
| --- | --- | --- | --- |
| 0–3 | 基础薄弱 | 不建议直接用于生产场景，应优先补充文档、边界与说明 | 信息缺失较多，步骤不可执行 |
| 4–6 | 可用但存在明显缺口 | 可在受控范围内试用，建议补充示例与异常处理 | 能理解部分流程，但复现稳定性不足 |
| 7–8 | 质量较好 | 可用于常规场景，建议持续补充维护信息 | 结构较清晰，执行路径较明确 |
| 9–10 | 高质量 | 可作为模板、基线 Skill 或复用对象 | 文档完善，风险控制较好，可审计性较强 |

### 方法论意义

从方法论上看，Insurance Skills 的质量评估框架同时关注三类核心问题：  
第一，Skill 是否被清楚定义；  
第二，Skill 是否具备足够的信息覆盖与执行依据；  
第三，Skill 是否在长期使用与风险控制层面具有可接受的稳定性。

因此，该框架不仅用于描述 Skill 的“质量水平”，更用于提升 Skill 的**可比较性、可审计性与可集成性**。

## 评分规则来源

Insurance Skills 的质量评分并非仅停留在文档层面，而是已在项目配置与处理流程中落地生效。LLM 主要用于补充部分维度的证据抽取，但并非唯一评分来源。平台最终强调的是结构化信号、规则映射与流程校验共同作用下的质量评估结果。

| 主题 | 结论 |
| --- | --- |
| 质量分范围 | 每个质量维度得分均为 0–10 |
| 质量维度 | clarity / completeness / operability / maintainability / security |
| 主流程生效规则 | 当前由 merge 阶段计算并写入质量字段 |
| LLM 补充 | LLM 用于补充 clarity / completeness / operability 的部分证据，但非唯一来源 |
| 边界校验 | 主分与子分均需满足 0–10 的范围约束 |

> 更完整的实现细节、映射逻辑与方法说明，建议单独放入 `docs/evaluation-framework.md` 或 `docs/methodology.md` 中，而不在 README 首页展开。
